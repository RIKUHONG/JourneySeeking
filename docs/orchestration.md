# P2-07 编排与 Critic

`TripOrchestrator` 在 service 层提供有限步骤的行程编排，不新增 HTTP 契约，也不依赖 LangGraph。它复用现有城市解析、候选池、知识检索、MoMA 生成、地图补全和天气补全。

## 执行顺序

1. 城市解析。
2. 按城市检索带来源的攻略片段；无结果或知识库失败时降级。
3. 生成并校验基础行程；生成器在内部采集可信候选池。
4. 记录候选池覆盖状态和不足原因。
5. 地图补全。
6. 天气补全。
7. 规则 Critic。

`StepRecord` 记录步骤名称、状态、来源、耗时、降级原因和失败类别。轨迹不包含完整 Prompt、API Key 或供应商原始响应。可选工具失败使用 `degraded`；生成或 Critic 等关键步骤失败不会返回未校验行程。

## Critic 规则

- 目的地、日期范围和每日日期必须与请求一致。
- 总费用不能小于活动费用之和，且不能超过用户提供的预算。
- `verified` POI 必须具有 ID、坐标和高德来源；存在可信候选池时，ID 必须属于该池。
- `verified` 路线必须具有可靠起终点坐标、路线对象和高德来源。
- `unknown` 天气不能携带天气状况、温度或来源等具体事实。

Critic 拒绝时抛出 `CriticRejectedError`，包含结构化 `CriticReport` 和截至失败点的脱敏轨迹。

## 限制与降级

`max_steps` 限制总步骤数，`step_timeout_seconds` 检查每步耗时。当前实现使用同步 integration，因此超时是在步骤返回后判定并拒绝结果，不会强制终止正在执行的底层网络调用；各供应商客户端仍须配置自身网络超时。

知识库缺失、检索失败或空命中不会阻塞基础生成。候选不足时生成器回退到非候选约束模式，并在轨迹中保留诊断。地图和天气仍遵循 P1 的可选补全降级规则。

## 离线验证

```powershell
python -m pytest backend/tests/api/test_orchestration.py -q
```

测试覆盖正常轨迹、RAG 降级、最大步骤、步骤超时，以及预算、POI 来源、路线和未知天气规则。
