# 团队工作面与协作

P2 已按现有专业边界完成主线交付；每个历史 Issue 的工作范围和验收条件见 [P2 Issue 清单](p2-issues.md)。P3 的设计基线、状态图和交付顺序见 [P3 Agent 化规划](p3-plan.md)。这些是主责分配，协作评审不改变集成责任人。

| 成员 | 核心 Issue | 条件 Issue | 主要文件/交付边界 |
| --- | --- | --- | --- |
| A | P2-01 契约、P2-04 存储 | 无 | 共享模型/OpenAPI、存储服务；先冻结契约，再实现版本服务 |
| B | P2-03 RAG、P2-05 单日编辑、P2-07 编排/Critic、P2-09 导出 | P2-C2 天气自动调度 | 知识检索、MoMA 编辑草稿、编排、规则校验和 Markdown/PDF 渲染；P3 Prompt、RAG 与 Critic 迁移 |
| C | P2-02 城市候选、P2-06 多轮上下文、P2-08 前端、P2-10 集成验收 | P2-C1 Redis | 地图候选、会话服务、前端工作流和跨模块端到端验收；P3 POI/天气前置与状态图联调 |

每个 Issue 由表中的成员集成，测试和文档随该 Issue 一起提交；P2-10 负责跨模块验收，不代替各功能 Issue 的测试。A 的 P2-01 应由 B/C 评审，B 的编辑/编排/导出由 A/C 评审，C 的候选/会话/前端/集成验收由 A/B 评审。修改共享模型或 `TripService` 前先在 P2-01 中确认字段和版本语义。每个 PR 关联 Issue，说明验证命令、契约/配置/迁移影响，至少一名非作者评审；不直接向 `main` 推送。

## P3 协作边界

- P3-01 状态图：由编排负责人维护 LangGraph 拓扑、State Schema、节点轨迹、修复上限和 legacy 回滚；A 评审契约，C 评审端到端观测。
- P3-02 天气前置与 7 天窗口：由 integration/地图负责人维护供应商分片、日期合并、覆盖率和权威回填；B 评审 Planner 上下文和提示词事实边界。
- P3-03 Prompt 工程：由 RAG/编排负责人维护 Prompt registry、版本、Schema 和离线 A/B；A 评审敏感信息与 API 兼容，C 评审前端可解释状态。
- P3-04 MCP 工具：工具 Schema、白名单、超时、重试、来源和 fake server 必须由 integration 与编排共同评审；不得让模型绕过 service 校验。
- P3-05 RAG 增强：先做评测和引用准确率，再决定混合召回或向量库；不得以检索升级改变天气事实来源。

P3 每个 PR 必须更新 [P3 Agent 化规划](p3-plan.md) 或相关契约文档，并说明图版本、Prompt/工具版本、降级和回滚影响。
