# 团队工作面与协作

P2 按现有专业边界分给 A/B/C；每个 Issue 的独立分支、工作范围、具体内容和验收条件见 [P2 Issue 清单](p2-issues.md)。这些是明确的主责分配，协作评审不改变 Issue 的集成责任人。

| 成员 | 核心 Issue | 条件 Issue | 主要文件/交付边界 |
| --- | --- | --- | --- |
| A | P2-01 契约、P2-04 存储 | 无 | 共享模型/OpenAPI、存储服务；先冻结契约，再实现版本服务 |
| B | P2-03 RAG、P2-05 单日编辑、P2-07 编排/Critic、P2-10 集成验收 | P2-C2 天气自动调度 | 知识检索、MoMA 编辑草稿、编排、规则校验和跨模块验收 |
| C | P2-02 城市候选、P2-06 多轮上下文、P2-08 前端、P2-09 导出 | P2-C1 Redis | 地图候选、会话服务、前端工作流和导出服务 |

每个 Issue 由表中的成员集成，测试和文档随该 Issue 一起提交；P2-10 负责跨模块验收，不代替各功能 Issue 的测试。A 的 P2-01 应由 B/C 评审，B 的编辑/编排/集成验收由 A/C 评审，C 的候选/会话/前端/导出由 A/B 评审。修改共享模型或 `TripService` 前先在 P2-01 中确认字段和版本语义。每个 PR 关联 Issue，说明验证命令、契约/配置/迁移影响，至少一名非作者评审；不直接向 `main` 推送。
