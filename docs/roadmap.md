## P2 历史执行顺序

1. 第一批：A 做 P2-01 契约；B 做 P2-03 RAG；C 做 P2-02 城市/候选，并可并行搭建 P2-08 前端框架。前端交互 mock 等 P2-01 契约初稿，跨界字段以其评审结果为准。
2. 第二批：A 做 P2-04 保存/版本；B 做 P2-05 单日编辑，并可在存储服务就绪前用 mock 开发；C 评审版本服务和编辑的会话交接，B 负责 P2-09 导出。
3. 第三批：C 做 P2-06 多轮状态和 P2-08 真实接口集成；B 做 P2-07 编排/Critic，C 负责 P2-10 全链路验收。

各 Issue 使用清单中的独立分支并单独提交 PR，从当时最新 `main` 创建。C 的 P2-C1 只有量化缓存/部署需求才启动；B 的 P2-C2 必须具备编辑、会话、编排和用户确认。两项均不计入核心 P2 完成条件。

## P3 执行顺序

1. 先冻结 [P3 Agent 化规划](p3-plan.md) 的状态 Schema、节点输入输出、天气证据契约和回滚开关，不直接替换现有 HTTP 契约。
2. 实现状态图和离线 fake 工具，完成 P3-01；图必须把 POI 搜索、RAG 检索和 7 天天气查询放在基础生成之前，并保留旧 `TripOrchestrator` 回滚路径。
3. 使用 Open-Meteo 完成最多 7 天的指定日期窗口、按日期去重和权威回填，再完成 P3-02 的生成前天气 Prompt 集成；Open-Meteo 一次覆盖 7 天，不需要模拟高德天气分片。
4. 建立 Prompt registry 和离线评测集，比较 P2 后置天气基线与 P3 前置天气版本，未达指标不切默认版本。
5. 接入 MCP 工具契约和本地 fake server，最后根据检索评测结果决定 RAG 的排序或混合召回优化。

P3 每个交付都必须同步更新状态图、节点/工具契约、降级规则、配置说明和验收记录。P3 不把天气驱动的已保存行程自动修改纳入基础生成图；该能力仍需用户确认和独立版本写入流程。
